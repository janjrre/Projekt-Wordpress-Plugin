## 2. Kann GitHub selbst Backups speichern? Ja, aber die Speicherart entscheidet.

| GitHub-Speicher | Technisch möglich? | Bewertung |
|---|---|---|
| **Normales Git-Repository mit Commits** | Pro Einzeldatei **100 MiB** hartes Limit; ab 50 MiB Warnung; Repository idealerweise unter 1 GiB | **NEIN als rotierende Sicherung**. Bei aktuellen 100–500 MiB Dateien könnten die Archive zu groß werden; jeder neue Commit bläht Git-Historie dauerhaft auf; Git ist kein Backupwerkzeug. GitHub empfiehlt selbst Spezial-Backup-Lösungen. |
| **Git LFS** | Erhöht Dateigrößenlimits, verbraucht aber eigene Speicher-/Transfer-Kontingente | **Nicht bevorzugt**, insbesondere nach bestehendem Billing-Stopp. Alte Versionen, Git-LFS-Kosten und Recovery müssen geprüft werden. |
| **GitHub-Actions-Artefakte** | Ja, aber zeitlich begrenzte CI-Dateien, für öffentliche Repositories **maximal 90 Tage**; Artefaktspeicher wird bei Kosten-/Kontingenten gesondert berücksichtigt | **NEIN als einziges Langzeitbackup**, und bei global blockierten GitHub-Runnern ist auch keine neue Sicherung darüber garantiert. |
| **GitHub Releases mit verschlüsselten Assets** | **JA**, je Asset maximal **unter 2 GiB**, bis **1.000 Assets je Release**; Assets per GitHub REST-API auch **direkt aus CircleCI** übertragbar, **ohne GitHub Actions** | Technisch mögliche **sekundäre Kopie oder Fallback**, vorzugsweise in **separatem privaten Backup-Repository**, aber kein speziell abgesicherter WORM-/Backup-Speicher. Verschlüsselung, Autorisierung, Versionen, Rotation, Löschschutz und echter Restore verpflichtend. Im **öffentlichen** Quellrepo wären Release-Dateien öffentlich herunterladbar – deshalb auf keinen Fall unverschlüsselt. |
| **Google Drive als unabhängiges verschlüsseltes Offsite-Ziel** | Bereits eigener privater Zielordner vorhanden; bisher **keine** CI-OAuth-Verbindung oder echten Uploads | **Bevorzugtes Ziel**, weil Quell-/CI-/Backup-Anbieter getrennt. Verschlüsselung **vor Upload**, Google OAuth nur mit ausdrücklich begrenztem Betreiber-Consent; Kein Backup-Abnahme-Status vor echtem Readback/Restore. |

**Offizielle GitHub-Belege:** [Große Dateien und Git-Grenzen](https://docs.github.com/de/repositories/working-with-files/managing-large-files/about-large-files-on-github), [GitHub Releases Limits](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), [Artefakt-Retention](https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-github-actions-artifacts-and-logs-in-your-organization), [LFS-Grundlagen](https://docs.github.com/de/repositories/working-with-files/managing-large-files/about-git-large-file-storage).

**Zusätzlich prüfenswert:** Ein separater privater Backup-Repository-Releases-Ansatz vermeidet öffentliche Dateien, aber er ist mit Quellcode/CI bei **demselben GitHub-Anbieter/Konto** korreliert. Eine Kontosperre, Accountkompromittierung oder Bedienfehler können zugleich Quellcode und Sicherungen betreffen. **Google Drive als zweiter Anbieter ist daher der stärkere Hauptschutz**, optional verschlüsselte private Releases als zusätzliche Kopie. Ein eigenes Repository kostet kein GitHub-Actions-Minutenbudget, solange **kein** GitHub-hosted Job dafür benutzt wird; GitHub-/API-/Abrechnungsrichtlinien für Speicher gelten trotzdem.

## 3. GitHub-Actions-Budgetstopp vs. öffentliches OrgaVela-Repository

GitHub dokumentiert: Standard-GitHub-hosted Runner sind bei **öffentlichen** Repositorys grundsätzlich kostenfrei, während das Freiminutenkontingent primär private Repositorys betrifft: [GitHub Actions Billing](https://docs.github.com/de/billing/concepts/product-billing/github-actions). Damit ist die **Dreamloud-Budget-Sperre des privaten Repos nicht automatisch ein unabhängiger Nachweis**, dass **ein** OrgaVela-Standardrunner ausgeführt werden oder nicht ausgeführt werden kann. Andererseits beschreibt GitHub bei einer **produktweiten Budgetobergrenze mit Stop Usage**, dass die **gesamte Kontonutzung GitHub-hosted Runner** blockiert sein kann: [GitHub Budgetregeln](https://docs.github.com/en/billing/how-tos/set-up-budgets). **Keine Annahme und kein ungewollter weiterer Trigger**, bevor die tatsächliche OrgaVela-Joblaufbarkeit/Budgetlage im Betreiberkonto kontrolliert wurde. Um die Ungewissheit sofort zu umgehen, ist CircleCI Free ein sinnvoller separater Ausführungsanbieter.

**CircleCI-Free-Grenze:** Offizielle [Credit-Dokumentation](https://circleci.com/docs/guides/plans-pricing/credits/) nennt **30.000 Free-Credits/Monat für persönliche Nutzung**, und bei **öffentlichen Open-Source-Projekten** separat bis zu **400.000 Credits/Monat** für Linux-Open-Source-Builds, abhängig von Qualifikation/Free-Plan-Bedingungen. Der **tatsächliche OrgaVela-Projektstatus, Free-Berechtigungen, Verfügbarkeit, Credits und Egress/Limits sind nicht verifiziert**. Wenn Credits = 0, werden Free-Jobs blockiert. Es darf **keine** kostenpflichtige Auto-Aufladung aktiviert werden.

## 4. Technisch sinnvolle Übertragung aus Dreamloud nach OrgaVela – ohne Projektvermischung

**Bevorzugte Architektur:**

```text
OrgaVela (eigenständiges IONOS-Hosting, SSH/WP-CLI, DB)
     │ Nur freigegebener konsistenter Leseexport; WordPress-Identität prüfen
     ▼
CircleCI Free (NEUES, eigenständiges Projekt für das ÖFFENTLICHE UOP-Repo)
     │ DB + notwendige WordPress-Dateien nur in flüchtiger privater Jobstufe
     │ Komplettes Backup und Manifest vor Netzwerktransfer mit Betreiber-Public-Key verschlüsseln
     ├──→ Privater Google-Drive-Ordner  ← empfohlenes dauerhaftes Ziel
     └──→ Optional: privates separates GitHub-Repo / Release-Assets ← zweite Kopie
                 (niemals Klartext/Private Key)
     │
     ▼
Verifizierter Re-Download, Hashvergleich, später echter isolierter Restore
```

**Sichere Umsetzungsreihenfolge:** (1) In CircleCI eigenständiges OrgaVela-Projekt mit genau ausgewählter Repo-Berechtigung und Free-Credit-Kontrolle einrichten; **nicht** das Dreamloud-CircleCI-Projekt als Zugang missbrauchen. (2) `.circleci/config.yml` erst als **rein synthetischen kleinen Offline-Smoke-Test ohne Secrets** mit möglichst geringen Credits und engem Push-/Branchfilter auf OrgaVela entwickeln und den echten Providerstatus prüfen. (3) Operator erstellt geschützten **projekt- und branchbeschränkten CircleCI Context**, prüft Schreib-/Push- und PR-Rechte; keine Secrets in untrusted Builds. (4) Im Secret-Context **neue OrgaVela-eigene** SSH-Zugangsreferenzen und das ausschließlich OrgaVela zugeordnete Cloud-Transportcredential hinterlegen; bestehende GitHub-`orgavela-ionos`-Environment-Secrets können **nicht automatisch von CircleCI gelesen werden**, und Dreamloud-Secrets bleiben unzugänglich. (5) Betreiber erstellt lokalen privaten Verschlüsselungsschlüssel; nur öffentlicher Empfängerschlüssel darf in CircleCI-Job-Konfig/Variables. (6) Zuerst ausschließlich eine **synthetische verschlüsselte Canary-Datei** zum ausgewählten privaten Ziel hochladen, zurückladen und Hash-/Entschlüsselung nachweisen; **keine** IONOS-/WordPress-Daten. (7) Erst danach echte **vollständige konsistente** OrgaVela-DB+Datei-Sicherung, *vor* dem Upload verschlüsselt, mit privater Aufbewahrung/Rotation und Error-Alerts. (8) Genau diese reale Kopie in eigener **offline-/netzwerkisolierter** WordPress/MariaDB-Testumgebung restaurieren, Mail/Cron/Webhooks verhindern, UOP 29 Tabellen/Indexstruktur, Default-Org, WordPress-Version und Datendateien verifizieren. Formal erst **dann** O03/B04/R03 signieren.

**Keinesfalls:** Eine Dreamloud-AuthID, Dreamloud-IONOS-Konfiguration, ein dortiges Secret oder dessen echten Backupdatensatz für OrgaVela verwenden. Duplicati ist **ein möglicher** transportfähiger Baustein, nicht verpflichtend: die UOP-`age`/rclone-Konzeption könnte ebenso über CircleCI laufen. Duplicati bringt eine zusätzliche OAuth-Vermittlerstelle, Backupvolumenformat und Secret-Provider-Gates mit sich; vor Übernahme muss es erneut unter dem OrgaVela-spezifischen Sicherheitsmodell getestet werden. Sollte GitHub Releases als Destination ausdrücklich gewählt werden, API-Schreibzugriff nur auf **ein separates** privates Backup-Repo beschränken, niemails ein Konto-weites PAT in öffentliche Joblogs/PRs geben.

## 5. Verbindlicher Status, Betreiberentscheidung und Stop-Gates

**Am 13.10.2026 wirklich nachgewiesen:** Dreamloud-CircleCI-Pilot hat mehrere **externe grüne** Runs; offizieller Duplicati-Linux-PoC ist lokal/synthetisch erfolgreich; OrgaVela-Backupwerkzeuge und synthetische Restore-Methode sind bereits geprüft; OrgaVela-Drive-Ordner privat vorhanden. **Noch nicht nachgewiesen:** CircleCI-Projekt für OrgaVela, autorisierte CircleCI-Kontexte/Secrets, echter Google-Drive-Canary, GitHub-Releases-Backup-Upload, unabhängiger dauerhaft gespeicherter OrgaVela-DB+Datei-Snapshot oder realer isolierter Restore. Keine produktiven Migrationen; O03 bleibt `partial`.

**Empfehlung:** **CircleCI Free als Ausführungsalternative prüfen und zunächst mit rein synthetischem Offlinejob validieren. Google Drive als primäres verschlüsseltes, unabhängiges Offsite-Ziel beibehalten.** Falls der Betreiber stattdessen (oder ergänzend) ausschließlich GitHub wünscht: **verschlüsselte GitHub-Release-Assets in einem gesonderten privaten Backup-Repo**, niemals regelmäßige Git-Commits in das öffentliche Quell-Repo. Diese Entscheidung kann später ohne Änderung des separaten Dreamloud-Projekts erfolgen.

**Weiterarbeit nur nach** Prüfung des eigenständigen CircleCI-Projektanschlusses und seiner Free-Quota (ggf. zunächst ohne Credentials), neuem Betreiber-Secret-Consent und erfolgreich gescheitertem Negativtest/positivem Canary. Keine neuen kostenpflichtigen Verträge und keine echte Sicherung ohne Verschlüsselung/Restore-Plan.
